# Cross-source Mechanic Matrix

Status: Historical planning record; lifecycle corrected after ADR-0008

## Purpose

This matrix extends the card-only cluster plan to every current executable source kind:

- `card`;
- `wizardProperty`;
- `deadWizardToken`.

The primary cluster is chosen by the object's main runtime mechanic, not by its carrier. A property or token should reuse the same Effect Runtime module as a card whenever the observable mechanic is the same. Carrier-specific code is limited to lifecycle adapters such as setup, activation ownership, Dead Wizard Token acquisition, resurrection context, and end-game token cleanup.

Existing wizard-property runtime is an implementation candidate to audit, not a reason to create a second handler. Dead Wizard Token draft presence is not runtime completeness.

This matrix records the allocation used by the now-closed GitHub issues #299–316. It is not an active implementation specification. Current rule semantics are owned by `docs/rules-canon.md` and ADR-0008; future corrections require new issues based on those sources.

Completion was tracked in two stages:

- `cardComplete`: the already delivered card backlog for a cluster is complete;
- `crossSourceComplete`: every applicable card, wizard property, and DWT is semantically mapped, present in the correct composition, and covered by focused tests.

All follow-up issues from this matrix are closed. Their local copies remain historical evidence and must not be treated as `ready-for-agent` work.

## Shared source and lifecycle contracts

- Every runtime effect must declare an exact `effectId × sourceKind × timing` policy. Do not widen all DWT effects globally.
- `EffectSourceContext` must distinguish card instances, wizard properties, and DWT instances instead of requiring card-only fields from every source.
- Death, DWT gain/replacement, reset and ordinary DWT text are separate stages. Gain/reveal happens before reset; only properties needed to compute that reset apply before it.
- Defer is determined by the immediate death source. If a concrete `AttackInstance` caused the death, reset happens immediately but ordinary one-shot and Ongoing text wait until the entire same instance closes, including all targets and redirects. Deferred items then start in turn order.
- A separate non-ATTACK death and a direct DWT gain resolve applicable ordinary text immediately and depth-first. A nested non-ATTACK death completes before returning to the interrupted DWT/effect; there is no global FIFO queue.
- Direct gain does not respawn the recipient and contextual one-shot text without a matching current death/respawn context fizzles permanently. Interception is direct gain for the actual recipient and does not cancel the victim's reset.
- DWT activations use their own legal-action adapter. End-game cleanup runs before the scoring snapshot.
- Consuming the last DWT does not interrupt the current action or remaining actions of the active player. The game ends in that player's end-of-turn procedure before the turn passes.
- `crossSourceComplete` requires runtime JSON, complete semantic mapping, correct stack quantity, focused tests against the real definition, and a blocking coverage report.

## Cluster impact

### Already implemented card-cluster PRs that need a cross-source audit or follow-up

- `dingler-status`: wizard property 001; DWT 007, 026, 027, 028.
- `chipsin-economy`: DWT 012, 015, 017, 021; shared payload in property 001.
- `ongoing-modifiers`: wizard properties 003, 007, 008; DWT 016, 020.
- `market-effects`: wizard property 004 is implemented; add only a real-definition regression test covering both halves.
- `life-total-effects`: wizard property 010; DWT 013, 014, 019, 025.
- `scoring-effects`: DWT 002, 003, 029 and the existing Dingler-inversion regression. DWT 005/016 store their complete numeric VP in their own primary-cluster PRs; DWT 026's status-gated scoring is delivered by `dingler-status` through the shared scoring module.

These closed card PRs remain `cardComplete`; their new sequential follow-ups establish `crossSourceComplete` without reopening the old issues.

### Paused or future cluster PRs to widen before implementation

- `special-card-stack`: extend #243's common transfer destinations and add separate issues for the shared death/DWT timing contract and for wizard property 002 with DWT 001/018 in the same PR. This first concrete DWT use introduces the shared acquisition adapter and deferred face queue.
- `activation-effects`: keep #264-267 and add explicit issue coverage for wizard property 005 and DWT 005 in the same PR.
- `dwt-interactions`: include DWT 022 and 023 as source-lifecycle slices alongside the cards that manipulate DWTs; do not move their reveal helpers into a separate implementation.
- `card-movement`: add wizard property 006 and DWT 006, 008, 009, 010, 011, 024.
- `attack-effects`: add wizard property 009 audit to #290; DWT 016 remains owned by `ongoing-modifiers` but reuses the same tagged-Wand attack module with different controller semantics.

### Shared dependencies, not separate carrier implementations

- effective card type: wizard property 003, DWT 001, 008, 014, 023;
- table-wide choice resolution: DWT 010, 011;
- deterministic multi-opponent traversal: DWT 012;
- death/resurrection context: DWT 007, 013, 014, 017, 019, 025;
- DWT acquisition/removal: DWT 003, 005, 022, 023, 027;
- effective scoring contributions: wizard property 004 and DWT 002/029; DWT 003 uses pre-scoring cleanup, while DWT 005/016/026 remain owned by their primary-cluster PRs;
- stable Wand classification: wizard property 009, DWT 016.
