# ADR-0010: PhysicalCardLedger и разрешение идентификаторов карт

## Контекст

У экземпляра карты есть стабильный `instanceId`, но runtime работает с
ветвью состояния, в которой важна именно branch-local identity объекта
`CardInstance`. Одного ID недостаточно: после `fork` тот же ID принадлежит
новому объекту, а поиск по всем зонам на каждой операции создаёт лишние
обходы, записи временных локаций и риск рассинхронизации контроля, владения и
физического расположения.

До этого решения `Control Ledger` был в основном реестром дескрипторов и
набором обходов. В тяжёлом профиле зафиксирована исходная стоимость:

- 1 214 045 точечных поисков физических карт;
- 272 352 102 просмотренных карты;
- 253 747 465 записей временных локаций;
- fingerprint исходной нагрузки:
  `f4f876588f0e685dc95fc7e3cab0183877764c738ac9bd30712cee85f540814f`.

Нужно было выбрать границу разрешения ID, ввести операции над живыми картами,
сохранить детерминированный порядок зон и обеспечить корректные fork,
rollback, временный контроль и диагностику без постоянной карты
`ID -> CardInstance`.

## Решение

Ввести `PhysicalCardLedger` как единственный модуль, который знает состав
встроенных физических зон, принадлежность карты ветви, текущую зону и
операции над зоной. Ledger владеет следующими зонами:

- шесть зон каждого игрока: `deck`, `hand`, `discard`, `playedThisTurn`,
  `permanents`, `unboughtFamiliars`;
- общие `mainMarket`, `legendMarket`, `mainDeck`, `legendDeck`,
  `wildMagicStack`, `limpWandStack`;
- отдельные стопки уничтоженных карт.

Внутренний путь — reference-first:

- известная живая карта передаётся в `locateCard`, `removeCard`, `moveCard`,
  `reorderCard` и `insertDetachedCard`;
- Ledger обновляет object-identity membership и проверяет дубликаты,
  принадлежность ветви, источник, назначение и ограничения зон;
- `clonePhysicalCardLedger` клонирует физические карты, сохраняет все
  внутренние ссылки на соответствующие клоны и устанавливает Ledger новой
  ветви;
- snapshot rollback восстанавливает массивы зон через Ledger;
- полная материализация `listPhysicalCardLocations` остаётся отдельной
  диагностической и аналитической операцией, а не внутренним способом
  перемещения карты.

Постоянная карта `instanceId -> CardInstance` не вводится. ID разрешается
только там, где его нельзя заменить живой ссылкой:

- `findCardInZone` — внешний ввод с уже известной зоной;
- `findPlayerCard` — player-scoped ввод для выбора карты;
- `resolveCardLocation` — редкая общая граница, когда зона заранее неизвестна
  и вызывающая сторона действительно располагает только ID.

После этой границы операции получают `CardInstance` и не выполняют обратный
поиск. Стабильные ID сохраняются только в сериализуемых проекциях, событиях,
выборах и диагностике.

## Реестр переведённых границ

| Контекст                               | Внутреннее представление                          | Граница ID или Ledger-операция                                   |
| -------------------------------------- | ------------------------------------------------- | ---------------------------------------------------------------- |
| `TemporaryCardControl`                 | `card: CardInstance` и `controllerId`             | `grantTemporaryControl` проверяет живую карту через `locateCard` |
| `EffectSourceContext` физической карты | живая `card`; synthetic source не содержит карты  | источник формируется на границе запуска эффекта                  |
| Входное действие по карте              | ID из действия                                    | `findCardInZone`, затем объектная операция                       |
| Выбор effective type                   | ID из выбора                                      | `findPlayerCard`, затем изменение живой карты                    |
| `GainedCardRecord`                     | необязательная живая `card`                       | ID остаётся только в проекции продолжения                        |
| Источники hand replacement             | `CardInstance[]`                                  | ID остаётся только в проекции продолжения                        |
| Удаление, перемещение и перестановка   | живая карта                                       | `removeCard`, `moveCard`, `reorderCard`                          |
| Полный список расположений             | `PhysicalCardLocation[]`                          | только Analyzer, инварианты, Defense и scoring                   |
| Fork                                   | клоны карт и bindings зон                         | `clonePhysicalCardLedger`                                        |
| Rollback                               | снимок порядка и состава зон                      | восстановление через `replaceZone`                               |
| Setup                                  | локальная сборка массивов до создания `GameState` | единственное явное bootstrap-исключение                          |

`EffectSourceContext` различает физический источник с живой картой и
синтетический источник без неё. Синтетический источник не получает карту
задним числом через ID-поиск.

`setup.ts` может собирать начальные массивы до установки Ledger, потому что в
этот момент runtime-состояние ещё не существует. После создания `GameState`
все перемещения, добавления, удаления, draw/refill, shuffle и rollback идут
через `PhysicalCardLedger`. Статическая проверка typed access блокирует
прямые изменения встроенных зон за пределами этой bootstrap-границы.

## Альтернативы

- Оставить поиск по ID и временные записи локаций. Это сохраняет старый API,
  но оставляет масштабирование по числу карт и расход памяти на каждую
  операцию.
- Ввести постоянную `Map<instanceId, CardInstance>`. Это ускоряет общий поиск,
  но добавляет второй источник истины, усложняет fork/rollback и требует
  синхронизации жизненного цикла каждого объекта.
- Передавать ID во всех контекстах и разрешать его непосредственно перед
  операцией. Это не устраняет повторные поиски и скрывает потерю branch-local
  identity.
- Разрешать каждому потребителю читать и менять массивы зон. Это сохраняет
  простоту локального кода, но возвращает параллельные правила membership,
  порядка и rollback.

## Причины выбора

Reference-first сохраняет уже выбранный branch-local объект, устраняет
обратный поиск из горячих внутренних путей и не создаёт второго реестра
идентичности. Три ID-операции остаются явными и локализованными на входных
границах. `PhysicalCardLedger` достаточно глубокий, чтобы инкапсулировать
membership, порядок, fork и обычные операции, но не становится владельцем
правил контроля, scoring или Effect Runtime.

## Последствия

### Положительные

- Одна карта физически принадлежит ровно одной зоне внутри ветви.
- Изменения зон и порядок карт проходят через один typed API.
- Fork и nested Defense rollback сохраняют соответствие живых ссылок и
  branch-local объектов.
- Внутренние операции не строят `PhysicalCardLocation[]` и не создают
  временные записи.
- Диагностика может отдельно измерять оставшиеся ID-границы и полную
  материализацию списка.

### Отрицательные

- Контексты, которые можно сериализовать, должны явно проецировать живые
  ссылки в стабильные ID.
- Новая физическая зона требует изменения набора дескрипторов и проверки
  статического guard.
- Hand-built тестовые фикстуры, меняющие массивы напрямую, нуждаются в
  последующем `assertConsistent` либо совместимом fallback-распознавании;
  production-код прямые изменения не допускает.
- Полный список локаций остаётся линейной операцией и не должен использоваться
  как замена обычному перемещению.
