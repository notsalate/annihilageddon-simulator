# ADR-0001: Модель benchmark и эпох производительности

## Контекст

Симулятор уже умеет выполнять воспроизводимые одиночные и массовые прогоны, но для будущих измерений нет общего правила, которое отделяет изменение игровой логики от изменения самого измерительного workload. Без такого правила эталон можно незаметно заменить актуальным результатом, а падение производительности — перепутать с изменением объёма работы.

Следующие измерительные срезы должны сравнивать массовую симуляцию и Best-Move Analyzer на поддерживаемой игре для двух игроков. Этот ADR задаёт модель сравнения и границы решения; benchmark harness, численные результаты и CI-блокировка создаются отдельными задачами.

## Решение

Вводится модель `reference` / `current` и последовательность performance epochs.

### Reference workload

`reference workload` — замороженный набор входов, который представляет поддерживаемый путь игры в конкретной эпохе. Он включает профиль workload, число игроков, seed и диапазон партий или поисковых профилей, лимиты, версию измерительного контракта и идентичность Runtime Data manifest. После принятия базовой линии reference не переписывается результатами текущего кода.

Reference должен покрывать тот же смысловой путь, который измеряется: для массовой симуляции — setup, ходы, розыгрыш карт, эффекты, сброс, reshuffle и подсчёт результата; для Analyzer — подготовку состояния, перебор, оценку, ранжирование и подготовку отчёта. Конкретные ступени и профили принадлежат соответствующим benchmark issue.

### Current workload

`current workload` использует тот же измерительный контракт и смысловой объём работы на актуальной игре. Он хранит собственный результат и отпечаток, но не становится новой reference-базой автоматически. Current сравнивается с reference только при совпадении epoch, workload fingerprint и протокола измерения.

### Workload fingerprint

`workload fingerprint` — хеш канонического JSON с параметрами работы, а не с номером commit. В него входят идентификатор профиля, число игроков, seed или диапазон seed, число партий либо лимиты поиска, `maxTurns` или эквивалентный лимит, идентификатор Runtime Data manifest и версия измерительного контракта. Роль `reference` или `current`, commit и параметры среды записываются рядом с результатом, но не маскируют изменение самого workload.

Если fingerprint различается, результаты считаются несопоставимыми и не получают автоматический performance verdict. Изменение fingerprint должно быть видимым в отчёте и объяснено изменением workload или правил.

### Performance epoch

Каждая принятая reference-базовая линия принадлежит именованной эпохе (`E0`, `E1`, ...). Новая эпоха создаётся, когда меняется игровая логика или явно принимается технический компромисс, который меняет измеряемую работу, её границы или смысл baseline. Обычный рефакторинг без такого изменения новую эпоху не создаёт.

Старая эпоха и её reference-результаты сохраняются. Переход в новую эпоху сопровождается ADR или обновлением существующего ADR с указанием прежнего правила, нового правила и долговременного последствия; reference-базовая линия не заменяется молча.

### Baseline и допустимая блокировка

Результат baseline хранит epoch, workload fingerprint, параметры измерения, отпечаток результата, сводку метрик и среду запуска. `current` может быть принят за новую reference-базу только после явного принятия новой эпохи или технического компромисса.

Performance gate может блокировать изменение только когда одновременно выполнены все условия:

1. корректность и воспроизводимость результата уже прошли свои проверки;
2. reference и current принадлежат одной эпохе и имеют одинаковые fingerprint и измерительный протокол;
3. измерение выполнено по объявленному числу прогревов и повторов, а результат пригоден для сравнения;
4. наблюдаемая метрика превышает явно объявленный budget конкретного профиля.

При несовпадении workload, отсутствии baseline, неполном отчёте или неподдерживаемой конфигурации проверка сообщает `incomparable` либо `not measured`, но не блокирует изменение скрытым порогом. Сам ADR не вводит CI и не угадывает budget; эти значения принадлежат benchmark-профилям и их отчётам.

## Альтернативы

- Одна подвижная reference, которая всегда переписывается последним прогоном. Отклонено: такой baseline не обнаруживает дрейф workload.
- Сравнение только полного времени без fingerprint и фазовых метрик. Отклонено: оно не отличает изменение объёма работы от регрессии реализации.
- Создавать новую эпоху для каждого рефакторинга. Отклонено: это обнуляет полезность исторического сравнения.
- Автоматически угадывать архитектурный смысл изменения по diff. Отклонено: решение об ADR требует явного прежнего правила, нового правила и последствия.

## Причины выбора

Разделение reference и current сохраняет стабильную точку сравнения, а fingerprint делает изменение входов наблюдаемым. Epoch связывает baseline с изменением правил и не заставляет обычные внутренние перестановки начинать историю заново. Явные условия блокировки позволяют использовать performance gate только для сопоставимых и воспроизводимых результатов, не превращая отсутствие данных в ложный failure.

## Последствия

### Положительные

- История базовых линий остаётся проверяемой после изменения игровой логики.
- Benchmark отчёт может объяснить, почему два результата нельзя сравнивать.
- Следующие benchmark-пакеты получают единые поля для reference/current, fingerprint и epoch.
- Архитектурное ревью не превращается в автоматическое угадывание по размеру или названию PR.

### Отрицательные

- Reference workload, manifest и бюджеты нужно поддерживать явно.
- Простое сравнение времени без подготовки fingerprint больше не считается достаточным доказательством регрессии.
- До появления benchmark harness и принятой baseline отсутствие данных будет давать `not measured`, а не блокирующий verdict.
