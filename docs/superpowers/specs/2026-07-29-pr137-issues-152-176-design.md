## Архитектура

1. Defense получает каноническое сопоставление `choiceId → legal Defense` до передачи options стратегии. Выбранный объект и его поля не являются источником истины. Обычная и redirect-защита проходят одну транзакционную последовательность: payment → movement → branch.
2. Effect Runtime Catalog остаётся единственной точкой decode, source-kind и runtime-mode policy. Consumers для effective values, resurrection и attack replacements вызывают узкие Catalog operations вместо чтения raw effect payload.
3. Player-controlled attacks используют общий attack profile и атомарный cost plan. `afterDamageDealt` и optional `topdeck_gained_card` проходят typed dispatch и choice boundary.
4. Control Ledger владеет physical card inventory для fork, scoring, lookup/removal и owner invariants. Consumers не перечисляют зоны вручную.
5. Регрессии живут рядом с владельцем поведения; финальный документ PR отражает только фактически выполненные проверки и остаётся draft.

## Исполнение

- Каждый issue получает одного `coder` и отдельный worktree, созданный от текущего интеграционного head.
- Задачи выполняются последовательно и коммитятся из worktree агента. Интеграционная ветка получает только проверенные коммиты.
- Каждое изменение начинает TDD-циклом: новый тест должен сначала упасть по ожидаемой причине.
- Общий объём worktree не должен превышать доступное место; зависимости устанавливаются только там, где это требуется для проверки.
