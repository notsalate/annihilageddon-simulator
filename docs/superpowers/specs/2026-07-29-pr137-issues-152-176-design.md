# PR #137: задачи #152–#176 — дизайн реализации

## Цель

Закрыть находки повторного ревью по задачам #152–#176 в draft PR #137, не меняя правила игры вне критериев приёмки.

## Проверенный статус интеграции

Текущий интеграционный head содержит технические исправления, перечисленные ниже. Этот документ не фиксирует окончательный SHA, результаты полного `npm run check`, отчёта кластеров или GitHub checks: они выполняются и записываются только после последующей интеграции всех коммитов.

- #152: стратегия получает неизменяемый снимок легальных вариантов защиты; исполнение и события используют каноническую Defense, определённую до вызова стратегии.
- #154, #162 и #163: матрица источников Catalog различает `card`, `wizardProperty` и `deadWizardToken`; raw effects сначала декодируются Catalog, затем проверяются timing и применимость.
- #164: замены атак проходят единственный Catalog-owned путь, включая Wand и ongoing sources.
- #167: результат `afterDamageDealt`, включая ошибку и `gameEnd`, возвращается через границу урона.
- #169: клонирование карточных зон строится по descriptors; metadata descriptor-зон неизменяемы и защищены от повторного вызова, подмены имени и общего состояния fork.
- #170: подсчёт VP обходит Ledger, но сохраняет прежнюю eligibility для scoring и результат `5:4`.
- #172 и #173: структурные AST-проверки контролируют полный inventory seam и архитектурные границы Catalog; coverage не зависит от параллельного перечня зон в consumer.
- #174 и #175 остаются выполненными без изменения своих границ.

## Архитектура

1. Defense определяется каноническим snapshot до передачи choices стратегии. Выбор стратегии — только идентификатор; mutable fields переданного объекта не участвуют ни в исполнении, ни в журналировании. Ordinary и redirect-защита соблюдают порядок payment → movement → branch.
2. Effect Runtime Catalog — единственная граница decode, source-kind и policy. `deadWizardToken` передаётся настоящим source context; consumers не читают raw `timing`, `effectId` или payload до Catalog.
3. Attack replacement и `afterDamageDealt` проходят типизированные Catalog/dispatch boundaries, поэтому ошибки и terminal result не теряются.
4. Control Ledger описывает physical card zones декларативно. Его descriptors используются для cloning, inventory guards и допустимого обхода карт для scoring, не расширяя eligibility игрока.
5. Архитектурные проверки #173 закрепляют публичные ownership boundaries устойчивыми AST и поведенческими тестами, а не текстовыми совпадениями исходников.
