# PR #137 issue 08 — защита публичных точек входа

## Контекст

Issue 08 требует отклонять прямой и транзитный реэкспорт decoder и
низкоуровневого Catalog через корневой API и production CLI. Предыдущий
эксперимент расширил эту задачу до анализа произвольного потока значений
JavaScript. Такой анализ не имеет конечной матрицы приёмки и не входит в
утверждённую модель угроз.

## Принятое решение

Guard защищает от случайных и агентских архитектурных регрессий в статическом
графе TypeScript. Намеренно обфусцированные обходы JavaScript остаются вне его
контракта.

Проверка строится на TypeScript `Program` и `TypeChecker`, использует реальное
разрешение модулей проекта и сопоставляет экспортируемые значения с их
каноническими символами.

## Защищаемая граница

### Защищённые источники

- исполняемые экспорты `src/engine/runtime-effect-decoder.ts`;
- низкоуровневые значения Catalog и registry, позволяющие обойти
  типизированные операции;
- локальные aliases защищённых значений внутри разрешённых потребителей.

Type-only символы decoder и Catalog не считаются исполняемой утечкой.

### Разрешённые потребители

Decoder как значение разрешено импортировать только:

- `src/engine/data.ts`;
- `src/engine/effect-runtime-registry.ts`.

Для этих доверенных адаптеров задаётся закрытый список разрешённых публичных
экспортов. Новый экспорт из адаптера требует явного изменения политики и
парных положительного и отрицательного тестов.

### Публичные точки входа

- `src/index.ts`;
- исполняемые CLI, указанные в `package.json`;
- публичные модули CLI, которые корневой API реэкспортирует явно.

Guard должен отклонять новую production CLI-команду, пока она не включена в
проверяемую политику.

## Алгоритм

1. Прочитать `tsconfig.json` стандартным TypeScript API и создать `Program`.
2. Завершить проверку ошибкой при диагностике конфигурации или невозможности
   разрешить проверяемый модуль.
3. Найти символ каждого защищённого модуля и его исполняемые экспорты.
4. Проверить импортные рёбра decoder:
   разрешённый файл, исходный модуль, имя символа и type/value-режим.
5. Для каждой публичной точки входа получить экспорты через
   `TypeChecker.getExportsOfModule`.
6. Разрешить alias через `getAliasedSymbol`, рекурсивно раскрыть namespace и
   остановить циклы множеством посещённых символов.
7. Отклонить экспорт, если его канонический символ принадлежит защищённому
   источнику или нарушает закрытый список доверенного адаптера.
8. Вывести диагностику с точкой входа, публичным именем и каноническим
   источником запрещённого значения.

Проверка не интерпретирует тела функций и не моделирует heap либо control
flow.

## Конечная грамматика проверки

Guard обязан понимать:

- named, default и namespace import;
- named, default, star и star-as export;
- import/export alias;
- простой верхнеуровневый alias в доверенном адаптере;
- статический доступ к свойству namespace;
- транзитные локальные реэкспорты;
- циклы статических реэкспортов;
- type-only import и export.

## Вне модели угроз

- `eval`, `Function` и сгенерированный код;
- `Proxy`, reflection и пользовательские helper-функции;
- поток значений через callbacks, closures, классы и контейнеры;
- `bind`, мутации и произвольные побочные эффекты;
- динамически вычисляемые module specifier и имена свойств;
- намеренное изменение guard, политики или её тестов;
- прямой файловый импорт собранного внутреннего модуля.

Если защита от этих случаев станет требованием, её следует реализовывать
физической границей пакета и `package.json#exports`, а не расширением
эвристического AST-анализатора.

## Проверки

Отрицательные fixtures должны покрывать корневой API и хотя бы одну CLI:

- прямой named export;
- транзитный named export;
- export-star;
- alias;
- default export;
- `NamespaceImport`;
- цикл реэкспортов;
- новый wrapper либо alias в доверенном адаптере, отсутствующий в политике;
- новую production CLI, отсутствующую в политике.

Положительные fixtures должны покрывать:

- type-only import/export;
- разрешённый типизированный адаптер;
- разрешённые операции Catalog;
- одноимённый независимый локальный символ;
- текущий `src/index.ts`;
- текущие production CLI.

После реализации выполняются точечные тесты guard, сам guard,
`npm run typecheck`, `git diff --check`, затем обязательный проектный
`npm run check`.

## Отклонённые варианты

### Продолжать анализ произвольного JavaScript

Отклонено: каждый новый синтаксический обход расширяет собственный язык
анализа, но не приближает проверку к доказуемой полноте.

### Самописное разрешение модулей

Отклонено: оно дублирует правила NodeNext и TypeScript для aliases, расширений,
циклов и реэкспортов.

### Физическое разделение пакетов в PR #137

Не входит в issue 08. Это более сильная долгосрочная граница, но требует
отдельного архитектурного решения и миграции структуры проекта.
