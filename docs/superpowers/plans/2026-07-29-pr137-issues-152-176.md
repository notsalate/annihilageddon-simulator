Этот документ сохраняет исходный план работ #152–#176. Он не является
доказательством их завершения и не содержит closing claims.

## Исторический снимок

были промежуточными. После него review зафиксировал достижимые контрпримеры

`REQ-R3-09-AC02` или `REQ-R3-09-AC03`.

Актуальная сверка ведётся в
`docs/superpowers/plans/2026-08-02-pr137-round4-review-fixes.md`; manifest
`tests/fixtures/pr137-round4-completion-reconciliation.json` привязан к
`2d2356231440e388adbbd9402db13b37108253c2`, где уже существуют указанные
в нём тесты. Он отмечает `REQ-176-AC01` и `REQ-R3-09-AC02` resolved, но
сохраняет `REQ-R3-09-AC03` открытым до устранения обходов checker и нового
Spec/Standards review.

## Исходная архитектура

1. Defense определяется каноническим snapshot до выбора стратегии; payment,
   movement и branch сохраняют установленный порядок.
2. Effect Runtime Catalog остаётся единственной границей decode и source-kind
   policy; consumers не читают raw payload.
3. Attack replacement и `afterDamageDealt` проходят типизированные границы
   Catalog/dispatch, не теряя ошибки или terminal result.
4. Control Ledger описывает физические зоны декларативно; descriptors владеют
   cloning, inventory и обходом карт для scoring.
5. Публичная поверхность decoder/Catalog защищена статическим TypeScript
   анализом с явными trusted adapters; произвольный JavaScript value flow вне
   этой модели.

Завершение допускается только после того, как reconciliation manifest называет
один полный CODE SHA для каждого active REQ, связывает его с контрпримером,
интеграционным fix commit, тестами и итогами Spec/Standards review. Успешный CI
сам по себе не заменяет доказательство поведенческого критерия.
